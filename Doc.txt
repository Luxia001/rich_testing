# Mini Project: Authentication & Role-Based Access System

## 1. Objective

พัฒนาระบบ Login โดยใช้ Angular สำหรับ Frontend และ Node.js + Express สำหรับ Backend โดยมีเป้าหมายเพื่อประเมินแนวคิดในการออกแบบระบบ Authentication, Token Management, Session Lifecycle และ Role-based UI

ระบบต้องรองรับ Remember Me ซึ่งส่งผลต่อระยะเวลาการเข้าสู่ระบบและการต่ออายุ Token รวมถึงการแสดงเนื้อหาที่แตกต่างกันระหว่าง Admin และ User

ไม่จำเป็นต้องพัฒนาเป็นระบบขนาดใหญ่ โดยให้ความสำคัญกับความถูกต้องของระบบ การจัดการกรณีผิดพลาด และเหตุผลในการตัดสินใจทางเทคนิค

## 2. Technology Stack

- Frontend: Angular + TypeScript
- Backend: Node.js + Express + TypeScript
- Database: เลือกใช้ได้ตามความเหมาะสม เช่น SQLite หรือ PostgreSQL
- Authentication: ใช้ Access Token และ Refresh Token หรือแนวทางอื่นที่อธิบายเหตุผลได้
- UI Library: เลือกใช้ได้ตามความถนัด

สามารถใช้ AI และ Documentation ช่วยพัฒนาได้ แต่ต้องสามารถอธิบายโค้ดและแนวคิดในการออกแบบของตนเองได้

## 3. Functional Requirements

### Part A: Login & Authentication

พัฒนาหน้า Login โดยมีองค์ประกอบดังนี้

- Email
- Password
- Remember Me Checkbox
- Login Button
- Error Message สำหรับกรณี Login ไม่สำเร็จ

ผู้ใช้ต้องสามารถ Login ด้วยบัญชีที่ระบบเตรียมไว้ให้ได้ โดยไม่จำเป็นต้องมีระบบสมัครสมาชิก

เมื่อ Login สำเร็จ ระบบต้องแสดงข้อมูลผู้ใช้ที่ Login อยู่ เช่น ชื่อและ Role

### Part B: Remember Me & Token Lifecycle

ระบบต้องรองรับการ Login สองรูปแบบ

**กรณีที่ 1: ติ๊ก Remember Me**

- ระบบต้องอนุญาตให้ผู้ใช้กลับมาใช้งานต่อได้ตามนโยบายอายุ Session ที่กำหนด
- เมื่อ Access Token หมดอายุ ระบบสามารถขอ Token ใหม่ได้โดยไม่ต้องให้ผู้ใช้ Login ใหม่ หาก Refresh Session ยังใช้งานได้
- หาก Refresh Token หมดอายุ ถูกเพิกถอน หรือไม่ถูกต้อง ต้องให้ผู้ใช้ Login ใหม่
- เมื่อ Refresh สำเร็จ ผู้ใช้ยังสามารถใช้งานต่อได้โดยไม่ต้องกรอก Email และ Password ใหม่

**กรณีที่ 2: ไม่ติ๊ก Remember Me**

- ระบบต้องใช้ Session แบบชั่วคราวตามนโยบายที่กำหนด
- เมื่อ Access Token หมดอายุ ระบบต้องไม่ต่ออายุ Session โดยอัตโนมัติ
- เมื่อ Token หมดอายุและไม่สามารถต่ออายุได้ ต้องนำผู้ใช้กลับไปหน้า Login
- หลัง Logout ต้องไม่สามารถใช้ Session เดิมเพื่อเข้าถึง API ที่ต้อง Login ได้อีก

ผู้สมัครต้องกำหนดและอธิบายอายุของ Access Token และ Refresh Session ให้ชัดเจน พร้อมอธิบายว่าระบบจัดการกรณีหมดอายุอย่างไร

หมายเหตุ: สามารถใช้เวลา Token ที่สั้นสำหรับ Demo เพื่อให้ทดสอบการหมดอายุได้จริง โดยไม่ต้องรอเป็นเวลานาน

### Part C: Role-Based UI

ระบบต้องรองรับผู้ใช้สอง Role ได้แก่ Admin และ User

หลัง Login สำเร็จ ให้แสดงข้อความตาม Role ดังนี้

**Admin**
- แสดงข้อความต้อนรับ Admin
- แสดงส่วน Admin Dashboard
- แสดงข้อความ เช่น "คุณสามารถเข้าถึงส่วนจัดการระบบได้"

**User**
- แสดงข้อความต้อนรับ User
- แสดงส่วน User Dashboard
- แสดงข้อความ เช่น "คุณสามารถเข้าถึงข้อมูลส่วนตัวของคุณได้"

ไม่จำเป็นต้องสร้าง Dashboard ที่มีฟังก์ชันซับซ้อน จุดประสงค์คือดูว่าผู้สมัครออกแบบการแยกสิทธิ์และการแสดง UI ตาม Role อย่างไร

### Part D: Authorization & Security

- Backend ต้องตรวจสอบ Token ก่อนอนุญาตให้เข้าถึง API ที่ต้อง Login
- Backend ต้องตรวจสอบ Role สำหรับ API ที่จำกัดสิทธิ์
- ผู้ใช้ที่ไม่มีสิทธิ์ต้องไม่สามารถเข้าถึง API ของ Admin ได้ แม้จะเรียก API โดยตรง
- ห้ามเชื่อถือ Role ที่ส่งมาจาก Frontend โดยไม่ตรวจสอบกับข้อมูลที่เชื่อถือได้
- Password ต้องไม่ถูกจัดเก็บเป็น Plain Text
- ต้องจัดการกรณี Token หมดอายุ ไม่ถูกต้อง หรือถูกเพิกถอนอย่างเหมาะสม

ผู้สมัครไม่จำเป็นต้องสร้างระบบจัดการ Admin แบบเต็มรูปแบบ สามารถใช้ข้อมูลบัญชีตัวอย่างที่เตรียมไว้ได้

### Part E: Logout & Error Handling

- มีปุ่ม Logout
- เมื่อ Logout แล้ว ผู้ใช้ต้องไม่สามารถใช้ Session เดิมเพื่อเรียก API ที่ต้อง Login ได้อีก
- หาก Token หมดอายุ ระบบต้องจัดการให้เหมาะสม
- หาก Refresh ไม่สำเร็จ ระบบต้องไม่วนขอ Refresh ซ้ำไม่สิ้นสุด
- แสดง Error Message ที่เหมาะสมเมื่อ Login ไม่สำเร็จหรือ Session หมดอายุ
- มี Loading State ระหว่าง Login และ Refresh Token ตามความเหมาะสม

## 4. Deliverables

1. Source Code ของ Angular และ Express
2. README ระบุวิธีติดตั้งและรันระบบ
3. บัญชีทดสอบ Admin และ User
4. สรุป Token Strategy ที่ใช้ เช่น อายุ Token และวิธีจัดเก็บ
5. วิธีทดสอบ Remember Me ทั้งสองกรณี
6. รายการสิ่งที่ทำเสร็จ สิ่งที่ยังไม่เสร็จ และข้อจำกัดของระบบ

## 5. Time Limit

- ระยะเวลา: 1 วัน
- ไม่จำเป็นต้องมีระบบสมัครสมาชิก
- ไม่จำเป็นต้องสร้าง Dashboard ที่มีข้อมูลซับซ้อน
- สามารถใช้บัญชีทดสอบและข้อมูลจำลองได้
- ให้ความสำคัญกับ Token Lifecycle, Security และแนวคิดในการออกแบบมากกว่าความสวยงามของ UI
